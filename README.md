# Якість пов’язаних тестових даних, згенерованих LLM

Репозиторій: [test-data-generation-research](https://github.com/nikogniko/test-data-generation-research).

Експеримент вимірює, як часто безкоштовні чат-моделі порушують обмеження бази даних і бізнес-правила, коли за один запит генерують пов’язані записи для інформаційної системи пошуку роботи для студентів (PostgreSQL, Prisma).

План: 3 моделі × 3 рівні обсягу × 10 повторів = 90 запусків. Кожен запуск — один запит у новому чаті; відповідь зберігається без змін і перевіряється валідатором за 22 правилами (1.1–3.10).

## Структура

```text
spec.json            специфікація: 8 таблиць схеми, довідники, рівні обсягу
requests/            тексти запитів, які надсилаються моделям
  request_S.txt …    запити рівнів S, M і L для основних запусків
  request_XL.txt     запит рівня XL (369 записів), використаний лише в пілоті
answers/             відповіді моделей, збережені без змін
  pilot/<модель>/    пілот
  main/<модель>/     основні запуски (файл .gitkeep зберігає порожню папку в репозиторії)
answers_anonymized/  знеособлені копії всіх відповідей (e-mail → userN@example.invalid, телефони → [masked])
  pilot/<модель>/, main/<модель>/   та сама структура, що й answers/
logs/
  pilot_log.xlsx     журнал пілоту
  run_log.xlsx       журнал основних запусків: інструкція, основні запуски, відхилення від протоколу
  blind_key.xlsx     ключ кодів для ручної перевірки наосліп
  blind_check.xlsx   форма ручної перевірки наосліп
results/             результати перевірки, які створює tools/run_all.py: книга Excel і текстовий файл
  pilot.xlsx, pilot.txt
  main.xlsx, main.txt
  lab7_dataset.xlsx  набір даних і результати аналізу (tools/lab7_analysis.py)
  lab7.txt           короткий підсумок аналізу
tool_check/
  tool_check.xlsx    перевірка інструментів на даних із відомим результатом
tools/               скрипти Python
```

Папка `blind/` з’являється після підготовки ручної перевірки (`tools/blind_check.py prepare`).

## Вимоги

Python 3.10 або новіший і пакет openpyxl:

```bash
pip install openpyxl
```

Усі команди виконуються з кореневої папки пакета.

## Моделі й налаштування

| Сервіс                       | Модель і режим                          | Чат                                      |
| ---------------------------- | --------------------------------------- | ---------------------------------------- |
| ChatGPT (chatgpt.com)        | GPT-6 Instant, режим міркувань вимкнено | тимчасовий                               |
| Gemini (gemini.google.com)   | 3.6 Flash                               | тимчасовий, якщо доступний, інакше новий |
| DeepSeek (chat.deepseek.com) | DeepThink і Search вимкнено             | новий                                    |

Основні запуски виконано на моделях, які сервіси показували під назвами «GPT-6», «4 Hydrogen» і «DeepSeek-V4.1-Flash»: зафіксовані версії на той час стали недоступні (аркуш «Відхилення» в `logs/run_log.xlsx`).

Використовуються безкоштовні облікові записи; поле власних інструкцій порожнє. Режими Auto (модель обирає сервіс) і пошук в інтернеті не використовуються. Перед основними запусками обидві виконавиці перевіряють, що в їхніх облікових записах доступні ті самі моделі. Назва моделі записується в журнал для кожного запуску; якщо інтерфейс її не показує (DeepSeek), записується назва, яку на запитання повідомляє сама модель.

## Рівні обсягу

| Рівень | Записів (не менше) | Використання                                                        |
| ------ | ------------------ | ------------------------------------------------------------------- |
| S      | 62                 | основні запуски                                                     |
| M      | 123                | основні запуски                                                     |
| L      | 246                | основні запуски                                                     |
| XL     | 369                | лише пілот (запит збережено в тому вигляді, у якому його надсилали) |

Склад кожного рівня (кількість записів у таблицях, статуси вакансій і відгуків) наведено в `spec.json` і в розділі «Обсяг і склад» запиту.

## Процедура

1. **Запуск.** Рядок аркуша «Основні запуски» в `logs/run_log.xlsx` визначає модель, рівень і файл відповіді. Увесь текст `requests/request_<рівень>.txt` надсилається одним повідомленням у новому чаті; відповідь копіюється й зберігається у файл із колонки «Файл відповіді». Правила заповнення журналу — на аркуші «Інструкція».
2. **Автоматична перевірка.**

   ```bash
   tools/run_all.py main     # основні запуски → results/main.xlsx, results/main.txt
   tools/run_all.py pilot    # пілот (logs/pilot_log.xlsx) → results/pilot.xlsx, results/pilot.txt
   ```

3. **Ручна перевірка наосліп.** У `logs/blind_key.xlsx` дев’ятьом відповідям (по одній на поєднання «модель × рівень») призначаються коди K-01…K-09. Далі:

   ```bash
   tools/blind_check.py prepare   # blind/K-01.txt … K-09.txt
   tools/blind_check.py compare   # висновки валідатора в logs/blind_check.xlsx
   ```

   Для ручної перевірки передаються лише папка `blind/` і форма `logs/blind_check.xlsx`; ключ кодів залишається в того, хто їх призначав.

4. **Аналіз, перевірки стійкості й знеособлення.**

   ```bash
   tools/lab7_analysis.py         # results/lab7_dataset.xlsx, results/lab7.txt, answers_anonymized/
   ```

   Скрипт рахує показники й рішення H1 і H2 за 90 запусками, виконує перевірки стійкості (S1–S3, A1–A3, окремо за виконавицями, без одного раунду), повторно перевіряє кожне знайдене порушення за текстом відповіді й створює знеособлені копії відповідей із повторною перевіркою валідатором.

5. **Перевірка інструментів** (не потребує відповідей моделей):

   ```bash
   tools/check_tools.py           # tool_check/tool_check.xlsx
   ```

## Результати перевірки

`tools/run_all.py` записує результати етапу у два файли з однаковим змістом: книгу Excel (`results/<етап>.xlsx`) і текстовий файл (`results/<етап>.txt`), який читається без Excel. Аркуші книги:

| Аркуш          | Зміст                                                                                                                          |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Запуски        | рядок на запуск: дані журналу, кількість записів, відхилення від заданого обсягу, частки порушених перевірок за групами правил |
| Правила        | для кожного запуску й правила — кількість перевірок «виконано», «порушено», «не оцінюється»                                    |
| Порушення      | кожна перевірка з результатом «порушено» або «не оцінюється»: таблиця, запис, деталі                                           |
| Модель і обсяг | медіана, Q1, Q3, мінімум і максимум загальної частки за 10 повторами (лише `main.xlsx`)                                        |
| Рішення        | застосування правил рішення H1 і H2 (лише `main.xlsx`)                                                                         |
| Повторюваність | у скількох повторах порушено кожне правило (лише `main.xlsx`)                                                                  |

У текстовому файлі ті самі дані подано розділами: запуски, обсяг відповідей, частки порушених перевірок, перевірки за правилами (для основних запусків — сума за 10 повторами кожного поєднання «модель × обсяг»), перелік порушень, а для основних запусків ще модель і обсяг, рішення й повторюваність. Номер запису в переліку порушень — позиція запису в масиві таблиці, від 1.

Правило 2.5 (дата завершення активної вакансії пізніша за дату запуску) подається окремо й не входить до часток, за якими перевіряються H1 і H2: у запиті немає дати, тож порушення 2.5 залежать від того, яку дату модель вважає поточною.

## Скрипти

| Файл                      | Призначення                                                                           |
| ------------------------- | ------------------------------------------------------------------------------------- |
| `tools/build_requests.py` | збирає тексти запитів рівнів S, M і L зі `spec.json`                                  |
| `tools/validate.py`       | валідатор однієї відповіді; окремий запуск виводить усі перевірки у файл Excel        |
| `tools/run_all.py`        | перевіряє всі відповіді з журналу й записує результати (книга Excel і текстовий файл) |
| `tools/analyze.py`        | підсумкові таблиці й правила рішення                                                  |
| `tools/blind_check.py`    | підготовка й порівняння ручної перевірки наосліп                                      |
| `tools/lab7_analysis.py`  | набір даних, рішення H1 і H2, перевірки стійкості, знеособлення                       |
| `tools/reference.py`      | генератор контрольних наборів (коректні дані кожного рівня)                           |
| `tools/check_tools.py`    | контрольні набори, пробні випадки з внесеними порушеннями й імітація підсумків        |
| `tools/make_logs.py`      | створює порожні шаблони журналу основних запусків і форм ручної перевірки             |
| `tools/xlsx_style.py`     | оформлення аркушів Excel                                                              |

Перевірка однієї відповіді з виведенням усіх перевірок:

```bash
tools/validate.py answers/main/gemini/gemini_M_01.txt M 12.11.2026 gemini_M_01_checks.xlsx
```

## Формати

- Дати в журналах — ДД.ММ.РРРР.
- Дати всередині згенерованих даних — один формат для всіх полів: дата й час ISO 8601 (РРРР-ММ-ДДTгг:хх:ссZ), бо Prisma для полів DateTime приймає лише дату з часом. Дату без часу валідатор позначає як порушення 1.4; правила 2.5, 3.8 і 3.9 для неї перевіряються за самою датою.
- Відповіді — текстові файли UTF-8 без жодних правок; файл, який не вдалося прочитати як JSON, є результатом запуску, а не помилкою даних.
